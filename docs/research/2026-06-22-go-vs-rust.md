# Go vs Rust Toolchain Spike

Date: 2026-06-22
Branch: `bulk-db-augment-plan`

## Goal

Choose the implementation language for the first `irrindex` tool before writing code.

The tool is expected to:

- fetch and stream-parse gzip-compressed public dumps
- parse simple RPSL route/route6/inetnum/inet6num fields
- parse RIPE RISWhois and CAIDA pfx2as line-oriented origin-prefix files
- store/query SQLite indexes
- emit line-oriented CIDRs for shell integration
- provide a small whois-compatible shim later
- run easily in GitHub Actions

## Decision

Implement the first `irrindex` in **Go**.

Use simple built-in parsers for the first source set:

- RPSL block/attribute parser for `route`, `route6`, `inetnum`, `inet6num`
- RIPE RISWhois parser for `asn prefix peer_count`
- CAIDA pfx2as parser for `prefix prefix_length as_field`

Treat Rust/BGPKIT as a deferred option for raw MRT parsing, not as the first implementation language.

## Rationale

The first useful deliverable is not a high-performance MRT parser. It is a shadow index and comparison/reporting tool that is easy to run in CI, easy to review, and easy to connect to the existing Bash/Python repo.

Go fits that first deliverable better:

- low CI setup cost with `actions/setup-go`
- straightforward static binary story
- excellent standard-library support for HTTP, gzip, line scanning, subprocesses, and CLI plumbing
- simple shell integration for `whois-shim`
- faster implementation velocity for a small repo utility
- enough ecosystem support for SQLite and basic RPSL parsing

Rust has real advantages:

- stronger parser correctness and memory-safety guarantees
- stronger BGP/MRT ecosystem through BGPKIT Parser
- stronger RPSL parser options such as `rpsl-rs`
- natural fit if raw MRT parsing becomes central

But those advantages matter later. The BGP dataset spike showed that the first observed-BGP source can be RIPE RISWhois dumps, with CAIDA pfx2as as an optional secondary source. Neither requires MRT parsing. For the initial shadow implementation, Rust would mainly increase implementation friction without unlocking required functionality.

## Go Library Notes

### SQLite

Options:

- `modernc.org/sqlite`: pure-Go SQLite driver for `database/sql`. Good fit for static/cgo-free builds.
- `github.com/mattn/go-sqlite3`: mature and widely used, but explicitly cgo-based and requires `CGO_ENABLED=1` plus a C compiler.

Sources:

- <https://pkg.go.dev/modernc.org/sqlite>
- <https://github.com/mattn/go-sqlite3>

Recommendation: start with `modernc.org/sqlite`. If performance is poor, benchmark `mattn/go-sqlite3` later in CI.

### RPSL

`rpsl-go` exists and targets parsing RIPE database responses, but its README says it is not a full RPSL implementation.

Sources:

- <https://github.com/frederic-arr/rpsl-go>
- <https://pkg.go.dev/github.com/frederic-arr/rpsl-go>

Recommendation: write a minimal field-preserving parser for the exact objects and attributes we need, then compare against real fixtures and IRRd/Rust parsers in the parser spike.

### BGP/MRT

GoBGP includes MRT parser packages, but it is a full BGP implementation rather than a focused dataset parser, and current Go package metadata shows multiple security advisories for the module.

Sources:

- <https://github.com/osrg/gobgp>
- <https://pkg.go.dev/github.com/osrg/gobgp/pkg/packet/mrt>

Recommendation: do not make GoBGP a dependency for the first version. Use RISWhois/CAIDA text files first.

## Rust Library Notes

### SQLite

Options:

- `rusqlite`: mature ergonomic SQLite wrapper.
- `sqlx`: async SQL toolkit with SQLite support.

Sources:

- <https://docs.rs/rusqlite/>
- <https://crates.io/crates/rusqlite>
- <https://docs.rs/sqlx/latest/sqlx/>
- <https://crates.io/crates/sqlx>

If Rust is used later, prefer `rusqlite` for this project because the tool is a local batch CLI, not an async service.

### RPSL

Rust has stronger RPSL parser candidates than Go:

- `rpsl-rs` / `rpsl` implements a parser and syntax tree for RPSL defined in RFC 2622/RFC 4012.
- `rpsl-parser` advertises an RFC 2622-conformant parser with low memory use and strong multiline handling.
- IRRd's Python code has mature RPSL parsing/validation and extracted metadata.

Sources:

- <https://docs.rs/rpsl-rs>
- <https://crates.io/crates/rpsl>
- <https://pypi.org/project/rpsl-parser/>
- <https://irrd.readthedocs.io/en/stable/development/architecture/>

This is Rust's strongest argument for the project. It is not enough to choose Rust for the first version because our initial parser needs are narrow, but it should influence the parser validation spike.

### BGP/MRT

BGPKIT Parser is the strongest Rust-specific reason to choose Rust. Its docs describe it as a performant, actively maintained, ergonomic MRT/BGP/BMP parser with remote-file support, transparent decompression, and built-in filters.

Sources:

- <https://github.com/bgpkit/bgpkit-parser>
- <https://bgpkit.com/tools/parser/>
- <https://docs.rs/bgpkit-parser/latest/src/bgpkit_parser/lib.rs.html>

Decision: defer. The BGP dataset spike showed that RISWhois dumps are enough for the first observed-BGP table. If raw MRT parsing becomes necessary, revisit Rust or use BGPKIT as a separate external stage.

## Split Architecture Option

The best long-term architecture can still include Rust without making the first tool Rust:

```text
irrindex (Go)
  fetches source manifests
  parses RPSL, RISWhois, CAIDA pfx2as
  builds SQLite
  queries origin/mnt-by
  emits comparison reports

optional bgpkit stage (Rust external binary)
  only if reports prove RISWhois/CAIDA are insufficient
  produces normalized TSV: source, family, prefix, origin_asn
  feeds irrindex build as another source file
```

This keeps the first deliverable small while preserving a clean path to Rust where Rust has clear leverage.

## Implementation Consequences

Update the plan as follows when implementation starts:

- Use Go for `irrindex`.
- Use `modernc.org/sqlite` unless a benchmark proves it inadequate.
- Keep `mattn/go-sqlite3` out of the first implementation to avoid cgo.
- Do not pull in GoBGP for MRT parsing.
- Do not implement raw MRT parsing in v1.
- Keep BGPKIT/BGPStream in "deferred source adapters" unless reports show a gap.
- Keep the parser spike, because a minimal Go RPSL parser still needs real-data validation.

## Final Recommendation

Use **Go** for the main tool now.

Use **Rust/BGPKIT later only if raw MRT parsing becomes necessary**.
